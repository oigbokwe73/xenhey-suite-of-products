## 3. Evaluation of your current implementation

The findings below come from the [linked page’s embedded source](https://www.xenhey.com/api/store/4D8DCB3864DF4F31BFF1BE5BC1E5B16C); linked pages were not separately tested.

| Area                | Observed implementation                                                   | Recommended change                                                   |
| ------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Product selection   | Three product cards with issuer-configuration disclaimers                 | Add side-by-side comparison and carry selected product into intake   |
| Intake              | Eleven-step wizard                                                        | Retain the structure; persist and restore every step                 |
| Dashboard           | Hard-coded balances and rewards alongside an underwriting request         | Separate pending-application and active-account states               |
| Draft saving        | Main wizard draft button stores step number and timestamp only            | Save the complete application, current step and stable record ID     |
| Step navigation     | Continue redraws the form without saving or validating the current fields | Save before navigation; validate when continuing                     |
| Step submissions    | Every step uses the same `cardApplication` storage key                    | Merge into one application instead of overwriting previous-step data |
| Final submission    | Logs a fixed sample application ID and displays a toast                   | Validate all steps and persist an actual submission                  |
| Field controls      | Shared generic dropdown options across unrelated fields                   | Define field-specific options, types and validation                  |
| Transactions        | Generic table reuses application sample rows                              | Supply transaction-specific records and columns                      |
| Application details | Links do not carry the selected application ID                            | Route with `recordId` and load the corresponding application         |

**Highest-priority fix:** the wizard currently risks losing entered values when switching steps. Address that before expanding its visual design.

## 4. Recommended customer screens

### Application workspace

Before approval, show:

* Selected product and requested limit
* Completion progress
* Outstanding documents
* Current review stage
* Last saved time
* **Continue application** and **View requests**

Do not show an available credit balance for an account that has not been opened.

### Active-card dashboard

After activation, show:

* Current balance and available credit
* Statement balance, minimum due and due date
* Pending transactions
* Payment and autopay status
* Recent purchases
* Employee spending
* Rewards and alerts

Keep application history accessible, but remove the onboarding tracker from the primary dashboard.

## 5. Recommended admin workspace

Organize existing review pages around a selected application rather than disconnected forms.

| Workspace               | Key information                                                                |
| ----------------------- | ------------------------------------------------------------------------------ |
| Application queue       | Business, requested product, requested limit, stage, reviewer and age          |
| Verification            | Business, ownership, identity and missing evidence                             |
| Credit and fraud review | Verified inputs, exceptions, recommendations and review history                |
| Decision                | Approved product, limit, pricing configuration, conditions and decision record |
| Fulfillment             | Account setup, card issuance, delivery and activation                          |
| Servicing               | Payments, disputes, delinquency, card controls and support cases               |

Customer-facing application status must remain separate from internal risk assessments and decision controls.

For Xenhey, retain the current Bootstrap styling and navigation foundation. Prioritize **reliable intake persistence → record-specific editing → separate application/account dashboards → dedicated card, transaction and payment screens**.
